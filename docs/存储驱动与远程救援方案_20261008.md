# 存储驱动覆盖 + 远程蓝屏救援 方案（2026-10-08，待拍板）

> 本文件里每条"实测"都是在当前活着的 VMware PE（build 2026-10-08 16:28:36，经 frps:8022 → pe-sshd）上跑出来的；标"待验"的目前没有证据。

## 0. 先回答问题：一般 PC/笔记本的盘能识别吗？

**能，而且覆盖面比想象的大。** 更正上一轮"148 个包全是 Net、存储驱动 0 个"的口径错误——那个数只统计了 `pnputil /enum-drivers` 里的 **staged 第三方包**，PE 的 **inbox 存储栈**根本没进那张表。重新按 `X:\Windows\INF` + `System32\drivers` 实测：

| 项目 | 实测结果 |
|---|---|
| inbox 存储类 INF | SCSIAdapter **48** 个、DiskDrive 4、HDC 3、CDROM 2、System 52（含大量芯片组） |
| inbox 存储驱动文件 | `storahci.sys` `stornvme.sys` `iastorv.sys` `amdsata.sys` `vsmraid.sys` `nvraid.sys` `disk.sys` `partmgr.sys` 都在 |
| iastorav | INF 在，`.sys` 不在（半截，需复核） |
| 缺失的关键驱动 | **`iaVmd`（Intel VMD，11~14 代默认开）= 0、`iaStorD`（新版 Intel RST）= 0、`amdrc`/`raidix64`（AMD RAIDXpert2）= 0** |
| 磁盘管理栈 | `Get-Disk` / `Get-Partition` / `Repair-Volume` 全部可用（WinPE-StorageWMI 已烘进镜像），`Win32_Volume=5 / DiskDrive=1 / Partition=3` 实测能枚举 |

结论分档：

- **直接看得见**：SATA AHCI 的机械/SSD、标准 NVMe（stornvme）、Intel 老平台 RST/AHCI（iastorv 覆盖）、AMD SATA（amdsata）、常见板载 RAID（vsmraid/nvraid 这类 inbox）、USB 大容量存储、光驱、SD 卡读卡器（USB 类）。绝大多数 10 代之前的台式机/笔记本 + 所有把 BIOS 设成 AHCI 的机器都在这一档。
- **看不见（真风险，就是现代主力机型）**：Intel **VMD 开启**的机器（11 代起默认开，NVMe 挂在 VMD 控制器后面，PE 里 `Get-Disk` 直接空盘）、新 Intel RST（iaStorD）、AMD RAIDXpert2 模式、以及部分第三方 HBA（JMicron/HighPoint/Adaptec/Promise，inbox 里那几个都没带）。
- **一个巧合证据**：这台 VM 自己的 Windows 里 `dism /Image:C:\ /Get-Drivers` 列出的 10 个第三方包中，第一个就是 `iastorvd.inf`（Class=SCSIAdapter，Intel）——也就是说"客户机装了 VMD 驱动、而 PE 没有"是完全现实的组合。

另外两个次要盲点（标"待验"）：BitLocker 真加密卷的 `manage-bde -unlock` 路径没测过（只测了 `-status`）；ReFS/存储空间卷能否在 PE 里挂载没测过。

## 1. Step 0：先量化，不改镜像（约 30 分钟，普通权限）

做一个 `storageprobe`（先热下发到 X: 验，通了再进镜像，一条命令出结果）：

1. `Get-Disk` / `Win32_DiskDrive` / `diskpart list disk` 三源对账，判"有几块物理盘、有没有被识别为未知设备吃掉"。
2. `pnputil /enum-devices /problem` 全量打印 code18/code28 的 **PCI VEN/DEV/REV + SUBSYS**，**不再只过滤网卡**——这就是"缺哪个存储驱动"的分母。
3. 探系统盘：`Test-Path <卷>:\Windows` + `manage-bde -status` 全卷 + 每卷 `Get-Partition`。
4. 输出一律英文 ASCII，落 `X:\storageprobe.txt`，并顺手 `type` 回来。

产出物 = 一张"机型 → 缺的 PCI ID"清单，Step 1 的选材全依赖它，别拍脑袋收驱动。

## 2. Step 1：驱动素材（需要你授权外网下载）

- 新增目录 `overlay\Drivers\Storage\`，与 `Net` 平行；体积预算 30~80MB，直接烘镜像，不靠现场下载。
- 选材顺序：① **Microsoft Update Catalog**（WHQL 签名，有 `Intel(R) RST/VMD`、`AMD RAID` 的 cab，本项目已有 catalog 手法）；② Intel 官网 RST/VMD 包 + AMD 官网 RAIDXpert2 作备选（直连不稳时按既有 ghfast.top 镜像手法）；③ 宿主机 DriverStore 现成的（有 iastorv/amdsata/vsmraid/nvraid，但版本偏老，只当兜底）。
- 必收清单（起步）：Intel VMD 全系（`iaVmd.sys`，覆盖 8086:09A0/1901/9A0B/A108/... 到 7FxE/51xE）、Intel RST AHCI/PCI（`iaStorD`/`iaStorAC`）、AMD `amdrc`/`raidix64`、常见 HBA（`jraid`/`mv91xx`/`percsas2`/`Adxcsi`/`i2o`）、以及 `AppleSSD`/`snd*`? 不要——只要存储类。

## 3. Step 2：构建与运行时打通（需要管理员 + 20 分钟构建）

1. `build.ps1` 加 `[4i]`：`DISM /Add-Driver /Recurse /ForceUnsigned` 注 `overlay\Drivers\Storage`，核对 DriverStore 增量；`BUILD_TAG.txt` 口径补一行 `storage inf N / ids M`（现在只报 Net，是自检盲区）。
2. `test\16_InjectNetDrivers.ps1` 加 `-Class Storage` 快路（boot.wim 已注入过时不必重跑 copype）。
3. `netdrvfix` → `drvfix/3.0`：索引从 `netdrv_index.txt` 扩成同时收 **Class=Net + SCSIAdapter + DiskDrive + VMD 所在的 System 类**；运行时 problem-code 分流沿用已验通的（18 → `pnputil /remove-device` + `/scan-devices`，28 → drvload，失败再 `/add-driver /install`）。
4. **成功判据换掉**：不再只看"网卡数 + IP"，改成 `sysdisk=ok|missing`（能不能看见 `C:\Windows`）+ 网卡双指标写进 `status.txt`。
5. 顺序保护：**先修网卡再修存储**。修存储会触发全设备重扫描，可能把正在承载 SSH 的网卡瞬断——通道一断就前功尽弃。

## 5. 验收怎么排才不白跑

- **VM 只能验"没退化"**：VMware 的盘是 SCSI/LSI 模拟、Hyper-V 是 storvsc，本来就看得见，**验不了 VMD**（同"VM 不能验 WiFi"那条教训）。
- **真正的验收只有一条路**：一台 11 代+（或明确开着 VMD/RST）的实机。顺序是先热补不重构建：BIOS 保持 VMD=RAID → 起 PE → 用 `storageprobe` 证明 `Get-Disk` 空 → 手工 `drvload iaVmd.inf` / `pnputil /add-driver ... /install` → **立刻出盘** 就算这条链路人通，再把驱动烘进镜像。省掉一次 20 分钟构建的赌博。
- 没有合适实机时：宁可只收 Catalog 全量驱动 + 让现场反馈补，也别宣称"覆盖 VMD 机型"。

## 6. 需要你定的三件事

A. **授权外网下载存储驱动**（Microsoft Update Catalog / Intel / AMD，走既有镜像手法）。
B. **验证机**：你手上有哪一代的实机能开 VMD？没有的话 Step 2 只能"烘进去但无法证明"。
C. **优先级**：先做 Step 3（救援 runbook + scp 回传通道，不依赖真机、我现在就能交付并静态验证）还是先做 Step 1+2（存储驱动，依赖 A/B）。

我的建议：**Step 0 + Step 3 先做**（都不需要真机、不需要管理员构建，能立刻把"远程救援"的成色抬起来），Step 1 的驱动素材同步开始收集，Step 2 等一台能真验收 VMD 的实机到位再一次性构建，避免反复 20 分钟 × N。

**顺带修掉的致命误判**：`storageprobe` 判 `SYSDISK` 时把 `TrimEnd('\')` 后的 `D:` 又拼了一次冒号，实际去 `Test-Path 'D::\Windows'` —— 永远 false，实机上一块明明装着 Windows 的 NVMe 被判成 `SYSDISK = missing`。已改为 `Join-Path`。教训：**只在 VM 里验过的判据不算验过**，VM 里那套"看得见盘"恰好让这条分支从未真正走通过。

**开 VMD 之后（因果链）**：BIOS 里 `Enable VMD Controller = Enabled` 重启进 PE ——
- BEFORE：`Get-Disk` **只剩 1 块**（U 盘），NVMe 和 SATA **一起消失**；`PCI\VEN_8086&DEV_467F` = `RAID Controller`、`code=28 CM_PROB_FAILED_INSTALL`；`DEV_7A62`（AHCI）从总线上不见了，说明 VMD 把 SATA 域也接管了；没有任何卷装着 Windows。存证 `C:\rescue\vmd-before.txt`。
- 取证手段本身也验通了：PE 自己用 `Invoke-WebRequest` 从 Microsoft Update Catalog 拉下 `iaStorVD 20.2.13.1038` 的 cab（1,335,541 B，8 秒，SHA256 `c9de738f…89d3`），`expand.exe` 解出 5 个文件，`pnputil /add-driver` 暂存成 `oem148.inf`（Class=SCSIAdapter）。也就是说**现场没有 U 盘驱动也能自救**。
- AFTER `drvload iaStorVD.inf`：drvload 回显 `Successfully loaded`，6 秒内 `Get-Disk` **1 → 3**，`DEV_467F` 变 `code=0 class=SCSIAdapter Intel RST VMD Controller 467F`，并枚举出两个 `Intel RST VMD Managed Controller 09AB`，`VOL D: windows=True` 恢复。存证 `C:\rescue\vmd-drvload.txt`。

**结论**：`overlay\Drivers\Storage` 里的 iaStorVD 确实能把"看不见盘"的 12 代机器救回来，而且走的是 code28 → `drvload` 这条 netdrvfix 已经支持的路径。**一个新发现的口径修正**：Intel VMD 打开后 **SATA 盘也会被 VMD 接管**，所以"普通 SATA 机器一定能看见盘"这句话要限定成"BIOS 是 AHCI 且 VMD 关闭时才成立"——救援现场必须先看 `storageprobe` 的 `UNBOUND_PCI`，不要凭"这是 SATA 盘"下结论。

**回退**：测完把 BIOS 的 VMD 关掉即可，D: 那套 Win10 恢复可启动（它是在 AHCI/直连模式下装的，VMD 开着会 `INACCESSIBLE_BOOT_DEVICE`）。

## 9. Step 2 落地：把存储驱动并进构建与开机自愈（2026-10-08 夜，代码侧已完成，等实机烧录验收）

### 9.1 先记一个真 bug：`&CC_` 让 Intel 存储 ID 整族静默消失

段感知索引第一次扫存储池时只报出 **9 个** ID，而全文正则口径能报 **21 个**。当时我把差值当成"这些 ID 属于不适用的更低段"，这是错的，真因在归一函数：

- Intel 存储 INF 里整片 ID 写成 `PCI\VEN_8086&DEV_9D03&CC_0106`（`&CC_` = 按 PCIe class code 限定匹配）。`iaAHCIC.inf` 30 个 ID、`iaStorB/T.inf` 各 7 个全都带这段。
- 设备实机枚举出来的 PnP 实例 ID 里**没有** `&CC_` 段（只有 `&SUBSYS_`/`&REV_`），所以 INF 侧的 `&CC_` 必须在归一时剥掉，两边才对得上。
- `test\NetDrvLib.ps1` 的 `Get-BaseId` 原来只 `-split '&SUBSYS|&REV'`，`&CC_` 留在字符串里 → `Test-PciBaseId` 的正则判它不合法 → **这批 ID 不是"段不适用"，是被当成非法 ID 直接扔了**。

修法（同一口径改两处，构建期和运行期必须一致，否则索引和查表对不上）：

```powershell
# test\NetDrvLib.ps1
function Get-BaseId([string]$id) { return (($id -split '&SUBSYS|&REV|&CC')[0]).ToUpper() }
# overlay\Scripts\netdrvfix.ps1
$hw -split '&SUBSYS|&REV|&MI|&CC'
```

修完的实测口径（`test\17_MakeNetDrvIndex.ps1 -SelfTest`，只对比不写文件）：

| 池 | INF | 段感知可绑 ID | 索引行 | 全文正则口径 | 段感知去掉的假命中 |
|---|---|---|---|---|---|
| `overlay\Drivers\Net` | 143 | PCI 684 + USB 147 = 831 | 1305（PCI 1060 + USB 245） | ID 611 / 行 1282 | **1 种**（例 `PCI\VEN_8086&DEV_10D6`） |
| `overlay\Drivers\Storage` | 7 | **PCI 21 + USB 0** | 21 | ID 21 / 行 21 | **0 种**（修复前只报 9） |

顺带两条口径结论：网卡池"每 ID 候选包上限 3"把 1531 行压到 1305 行（88 个 ID 被截，单 ID 最多曾有 37 个候选）；存储池 21 个 ID 每个只有 1 个候选包，没有截断，也没有"死包"（网卡池有 9 个 INF 绑不出任何 ID）。修复后重扫的网卡索引与修复前**逐字节一致**，`test\verify_netdrv.ps1` 仍 GATE PASS，说明这次改动没有把网卡那一半带偏。

### 9.3 `netdrvfix` 升 3.0：两轮分工 + 盘的硬判据

- **查表两份索引**：`netdrv_index.txt`（网卡）+ `stodrv_index.txt`（存储）。后者缺了只 `WARN = storage index missing ... (this ISO predates v3)`，**不 ABORT** —— v3 脚本落进 v2 老镜像也要能把网卡那一半修完。
- **顺序 = 先网卡后存储**：网卡先起来才有 SSH/frp/下载通道；存储不依赖网络，放后面不影响救援；顺带避开"重扫盘导致承载 SSH 的网卡瞬断"。
- **存储这轮只碰 `PCI\VEN_` 键**：`Get-DevClass` 里写死 —— 哪怕某个 `USB\VID_` 撞进存储索引也不给它 `pnputil /remove-device`，免得把正在读日志的启动 U 盘摘掉。`-SkipStorage` 整轮关掉。
- **判据加两条硬证据**（`drvload` 的返回码永远不能当判据，见第 3 节）：`Get-Disk` 台数 before→after、固定盘（`DriveType=3`）上有没有 `\Windows` → `sysdisk=ok|missing`。`Get-SysDisk` 明确跳过 ramdisk 盘符，因为 `X:\Windows` 一直都在，把它算进来等于永远自欺欺人。
- **`STOR` token**：`ok`（系统盘可见）/ `partial`（绑上了、盘数涨了但没 `\Windows`）/ `noop`（本来就没得修）/ `fail`（什么都没绑上）。`X:\status.txt` 单行现在是 `netdrvfix=<tok> bound=.. adapters=.. ip=.. stor=<tok> disks=a->b sysdisk=<t> remain=<kind:key=codeN>`，配套 `NEXT(stor)` 指路；`niccheck` 的 `VERDICT` 尾部也追加了 `disks=<n> sysdisk=<tok>`，并新增 `[2b] STODRV` / `[2c] DISKS` / `SYSDISK` 段。
- 顺手修掉一个潜伏 bug：`Get-UsbLetters` 里 `Win32_LogicalDisk.DeviceID` 在不同版本可能是 `G:\` 而不是 `G:`，原来 `^[A-Za-z]:$` 匹配不上 → **日志自动拷到 U 盘这条分支可能从来没真正触发过**。两处（`netdrvfix` / `niccheck`）都加了 `TrimEnd('\')`。

**7 个包只进了 6 个，而构建脚本报了成功。** 两层原因叠在一起：
